# 三色屏（SSD1680）阶段性研究

同一块板子换上 2.9 寸**三色**屏（黑白红，SSD1680 / `GxEPD2_290_C90c`）之后做的一串实验。

**状态：耗时规律已定论，快刷通道未打通。** 这一支的目标和黑白线（IL3820，见仓库根 README）不同：
三色屏多了红色粒子，OTP 里的波形相数天然更多，出厂全刷 **27.2 秒**，比黑白屏的 1.65 秒慢一个数量级。
下面这些固件记录了已经试过的方向、拿到的数字，以及走不通的地方。

已经站得住的：温度覆写把全刷压到 **5.1 秒**；区域刷耗时只跟**门线数**走
（`t ≈ 0.76 s + 0.0147 s × 扫描行数`，五块屏极差 1.3%）；`0xC8` 的 90ms 是**空转**，
四种做法都刷不出画面。

写在这里的价值是：**别重复踩**。每个目录对应一个具体问题，第一行注释就是它要验证什么。

## 硬件

| 部件 | 参数 |
|---|---|
| 电子纸 | 2.9 寸，128×296，三色（黑/白/红），SSD1680 |
| 驱动类 | `GxEPD2_290_C90c`（三色）/ `GxEPD2_290_T94`（黑白，用于对照） |
| 接线 | CS=GPIO15, DC=GPIO0, RST=GPIO2, BUSY=GPIO4 |
| 板子 | 甘草酸不酸 2.9 寸 SD 墨水屏阅读器板（ESP8266） |
| 两个平面 | `0x24` = BW 平面，`0x26` = RED 平面 |

屏上标签 `E029A1ON1842xx` **不写控制 IC**，所以第一件事是用 `epd_probe/` 逐个型号试出来 ——
最终确认是 SSD1680，三色。

## 三条已经站得住的结论

### 1. 温度覆写能把全刷从 27.2 秒压到 5.1 秒

SSD1680 的 OTP 里按温度区间存了不同相数的波形，高温区间的波形相数少得多。
`0x1A` 强写温度寄存器，再用 `0x22 = 0xD7`（含 `0x10` Load LUT）让它**在不重读温度传感器的前提下**
按这个温度去挑 OTP 波形。实测（`epd_temp_sweep`）：

| 配置 | 全刷耗时 | 相对基线 |
|---|---|---|
| `0xF7` 基线（读传感器，室温 19℃） | 27173 ms | 1.0× |
| `0xD7` + 100℃ | **5116 ms** | **5.3×** |
| `0xD7` + 80℃ | 5117 ms | 5.3× |
| `0xD7` + 65℃ | 11163 ms | 2.4× |
| `0xD7` + 50℃ | 11162 ms | 2.4× |
| `0xD7` + **10℃**（反向对照） | 35429 ms | **0.77×** |

最后一行是这组实验的关键：**故意往低温写，它比基线还慢**。如果温度只是一串被忽略的字节，
不可能出现这种单调关系 —— 这条反证排除了"数字是巧合"的可能。

代价是墨色。100℃ 那档 5.1 秒，但黑不够黑、细线发糊；65℃ 的 11.2 秒档在速度和观感之间更平衡。
`epd_wave_abc` 把这三种波形刷在同一张屏的三个横条上做同屏对比，`epd_fast_ab` 做上下半屏对比，
都是为了让"糊到什么程度"能直接用眼睛判断，而不是靠描述。

### 2. 局部刷新的时间只跟**门线数**走，跟面积无关

这一条和黑白线的 `T = MUX × T_Gate` 模型是同一个物理规律。`epd_dir_test` 用五种面积/形状组合测：

| 图案 | 窗口 | 面积占比 | 门线数 | 实测 |
|---|---|---|---|---|
| 细横带 | 296×16 | 12.5% | **296** | 5198 ms |
| 粗横带 | 296×64 | 50.0% | **296** | 5268 ms |
| 右竖带 | 144×128 | 48.6% | **144** | 3022 ms |
| 右竖带 | 72×128 | 24.3% | **72** | 1914 ms |
| 左竖带 | 144×128 | 48.6% | **144** | 3023 ms |

面积 12.5% 的细横带（5.2 秒）比面积 48.6% 的竖带（3.0 秒）**更慢**，因为前者的门线数是后者的两倍。
左右位置对调完全不影响结果，所以也不是边缘效应。

实用推论：**想局部刷得快，要把窗口压成"矮而宽"，不是"小而方"。**
`epd_region_test` 进一步按门线数扫了一遍（296 / 160 / 100 / 56），耗时基本落在
`固定开销 + 门线数 × 单行时间` 这条线上，56 行只要 5.98 秒。

同一条规律后来在**五块屏**上各跑一遍（脚本 VM，不重编译），耗时极差 1.3%，
拟合出 `t ≈ 0.76 s + 0.0147 s × 扫描行数`，五块屏的半程比全部是 0.575 —— 可以当型号常数用。
细节和"BUSY 接触不良会伪装成屏变快"这个坑，见 `partial-refresh.md` 的「五屏复现」。

### 3. 局刷会衰减，必须定期全刷

`epd_region_stress` 连续做 10 次 `h=56` 的区域刷（每次内容都变），观察窗口外的画面。
下方不动的参考图会逐次变淡，10 次之后需要一次全刷才能完全复原。
`epd_ui_demo` 因此设成 **5 次局刷后做一次全刷清底**，这个比例在时钟场景下观感可以接受。

局刷本身约 **3.0 秒**（`_Update_Part` 实测 2887 ms），全刷 27.2 秒 —— 清底一次等于牺牲 9 次局刷的时间。
三色屏做交互界面的真实体验就是被这个比例卡住的。

### 4. `0xC8` 的 90ms 是空转，刷不出画面

`bwfast.md` 记录过 `0xC8`（Mode 2）只要 92ms，并写过「画面判据全部通过」。
但在 ① 号屏（`E029A10N184274`）上复现时，**四种上传/触发方式全部只跑波形、不出画**：

| 触发方式 | 耗时 | 画面 |
|---|---|---|
| `0xC8` 直接触发 | 90~91 ms | 全白 |
| `0xC4` / `0xCC` | 242 / 243 ms | 全白 |
| `0xF8`（载 OTP 表 + Mode2） | 94.3 ms | 全白 |
| `0xC0` 上电 + `0x32` 写 LUT + `0xC8` | 90.2 + 91.1 ms | 全白 |
| 自建帧缓冲裸写 `0x24`/`0x26` + `0xC8` | 90.6 ms | 全白 |
| `0xD7` @100℃（对照） | **5116 ms** | **正常** |

这 90ms 极其稳定（抖动 <1ms），最容易误判成"波形在跑、只是对比度不够"。
实际更可能是：**三色屏 OTP 里只烧了 Mode 1 的三色波形，Mode 2 是空的。**
`0xD7` 能出画，因为它带温度覆写、走完整三色波形。

排查过程中还挖出一个更基础的 bug：`expSetRamArea()` / `expWriteRam()` 用的是**物理坐标**，
而横屏固件里 `W`/`H` 是逻辑 296×128。传错了会把 X 地址写到 36（物理上限 15），
数据全部丢失且不报任何错。这个坑比 `0xC8` 本身更难查。

**待确认**：`bwfast.md` 那次成功没写明哪块屏。换 ⑤ 号屏跑同一固件即可判定是屏个体差异
还是这条通道整体不可用。完整记录见 `ui-clock.md`。

## 走不通 / 没走完的地方

诚实记录，这些都是当时真实卡住的位置：

- **`0xC8`（Mode 2）的 90ms 出不了画。** 这是最接近目标的一条路，也是最容易误判的一条：
  耗时稳定、BUSY 正常、SPI 无误，就是屏幕不动。四种上传/触发组合全试过，见上文结论 4。
  目前唯一能稳定出画的通道是 `0xD7`（5.1 秒 / 65℃ 时 11.2 秒）。
- **三色屏没有找到类似黑白线的"单相快刷"路径。** 黑白线的关键是 `0x32` 直接写 30 字节 LUT，
  把 `sumTP` 压到 1。SSD1680 的波形结构更复杂（两个平面 + 红色粒子的双向迁移），
  直接砍相数会立刻出现红色不上色或黑红互串。这条最有价值的路**没有打通**。
- **`epd_bw_partial` 的路线被否定**：用黑白驱动刷三色屏，全刷正常且快，但红色粒子完全不动，
  留在屏上成为不可消除的残影。
- **看门狗坑**：早期用 `ESP.wdtDisable()` 想"别让看门狗打断长刷新"，
  结果 core 3.x 里它只关软件看门狗，硬件看门狗 8 秒照样硬复位 —— 刷新中途被打断，画面发淡，
  看起来像"电压不够"。`epd_3c_clean` 里那段注释就是这次教训。
- **`0x08` INITIAL DISPLAY 会超时 6 秒并扰乱时基**，不要用它计时。
- **27 秒的全刷意味着这块屏做不了"实时"应用**，除非接受 5.1 秒的糊版。
  如果目标只是天气时钟这类分钟级更新，现在的 3 秒局刷已经够用。

## 依赖与已知问题

- 需要 `GxEPD2`、`U8g2_for_Adafruit_GFX`（`epd_ui_demo` / `epd_font_test`）、`Wire`（传感器）。
- `epd_font_test` 依赖 `cn_font.h`（20px 点阵中文字库），**没有放进仓库**。
  它由 `tools/gen_cn_font.py` 从本机字体生成，字体版权归字体厂商，不入库。用法见脚本头部注释。
- `epd_ui_demo` 用到 `epd_panel.h`（型号表 + 驱动选择）与 `epd_time.h`（编译时注入时间基准），
  都是自写文件，随固件一起在目录里。
- 部分早期日志因串口波特率不匹配是乱码，没有整理进来；结论以本文件为准。
