# 横屏三色时钟界面：按键、刷新通道，和一次失败的快刷

本文记录 `epd_ui_fast` 这个固件（横屏中文时钟 + 菜单 + 阅读 + 清单）的开发过程，
重点是三个真实踩过的坑：**按键 IO 的物理真相**、**`0xC8` 快刷为什么刷不出画面**、
以及**区域刷新在这套屏幕上到底能省多少时间**。

测试屏：① 号（`E029A10N184274`）。

---

## 1. 硬件真相：这块板子到底有几个键

原厂固件（甘草酸不酸 V14/V15）是**三键**语义。但在我们这块板子上，可编程的键只有两个。
这不是适配不到位，是物理限制。证据来自 PCB 网表（`.epro2` 工程文件里的 `PAD` / `PAD_NET` 记录）：

| 物理按键 | 接到 | 依据 |
|---|---|---|
| 按键 1 | **RESET** | 直接拉低 RST，不经过任何 GPIO |
| 按键 2（中间） | **GPIO0** | `GPIO0` 网络连 5 个焊盘，含 ESP-12F 18 脚；且与屏的 DC 线共用 |
| 按键 3（右边） | **GPIO3 / RX** | 网表有 `RX` 网络、**没有 `GPIO3` 网络**，连 21 脚 |

原厂 V2.3X 起把按键 3 从 GPIO5 改到了 GPIO3（RX），因为 GPIO5 要让给 SD 卡的 CS。

ESP-12F 的 22 个脚全被占满：

| 引脚 | 网络 | 用途 |
|---|---|---|
| 1 RST | GPIO16 | 复位键 + 深度睡眠唤醒短接 |
| 2 ADC | ADC_IN | 电池电压 |
| 3 CH_PD | CH_PD | 使能 |
| 4 GPIO16 | GPIO16 | 唤醒 |
| 5 GPIO14 | CLK | SD SCLK |
| 6 GPIO12 | DATA0 | SD MISO |
| 7 GPIO13 | CMD | SD MOSI |
| 8 3.3V | 3.3V | 电源 |
| 15 GND | GND | 地 |
| 16 GPIO15 | GPIO15 | 屏 CS |
| 17 GPIO2 | GPIO2 | 屏 RST |
| 18 GPIO0 | GPIO0 | **屏 DC + 按键2** |
| 19 GPIO4 | GPIO4 | 屏 BUSY |
| 20 GPIO5 | DATA3 | **SD 卡 CS**（不是空闲） |
| 21 RX | RX | **按键3** |
| 22 TX | TX | 串口输出 |

ESP-12F 模块底部露出的那 5 个焊盘，是侧边同一批引脚的另一面，不是额外 IO。

**如果要加蜂鸣器**，只剩两处夹缝：

- **GPIO1（TX）**：正式固件关掉串口就能当普通 IO，代价是没有串口日志。
- **GPIO5（SD CS）**：只有完全不用 SD 卡时可行。

不能动的：GPIO0（读键时要切成输入，输出脉冲会让屏收到乱码命令）、GPIO3（按键3）、
GPIO12/13/14（SPI 总线）、GPIO16（接 RST，一动就复位）。

## 2. 按键驱动：三个必须记住的坑

### 坑一：GPIO3 是 UART 的 RX，串口开着时上拉会失效

写完按键代码后，右键完全没反应。加电平诊断后看到：

```
[电平] K0=1 K3=1     ← 松开
[电平] K0=0 K3=1     ← 中键按下，K0 正常变 0
[电平] K0=1 K3=1     ← 松开
```

**K3 从头到尾恒为 1，从来没变成 0**。但之前 `kp7.log` 那次全 IO 扫描明明能读到 G3。

原因：`pinMode(INPUT_PULLUP)` 只在 `setup()` 里设一次，而 **UART 外设会周期性把 GPIO3
的模式抢回去，内部上拉随之失效**，悬空就恒定读成低电平。

后果比"读不到"更糟：代码里 `r = (digitalRead == LOW)`，于是软件认为右键**一直按着**，
每 600ms 自动触发一次「长按 = 确认」，把用户反复弹进阅读页。表现就是"按什么都没用"。

修法（两个都要）：

```cpp
// ① 每次读键前重设一次上拉，而不是只在 setup 里设
static bool readKeyR()
{
  pinMode(KEY_R, INPUT_PULLUP);
  return digitalRead(KEY_R) == LOW;
}
```

```cpp
// ② 卡死保护：一个键连续按住超过 10 秒，判定线路异常，忽略它
if (r && krDown && now - krDown > KEY_STUCK_MS) { r = false; }
```

另外顺带确认了一件事：`Serial.end()` 之后 GPIO3 立刻回到高电平（串口关闭时 `K3=1 K0=1`），
验证了「UART 抢上拉」这个判断。

**注意**：不要试图用 `Serial.begin(115200, SERIAL_8N1, SERIAL_TX_ONLY, 1)` 来"把 RX 让出来"。
实测这样改之后 `digitalRead(GPIO3)` 读到的是 **UART 外设的空闲高电平**，不是引脚真实电平，
按键会更彻底地失效。

### 坑二：GPIO0 和屏的 DC 线是同一根

读中键时必须把 DC 线临时切成输入上拉，读完立刻切回输出，否则后面的 SPI 数据会全被当成命令。
所以按键扫描是**轮询**，不能用中断。

还有一个启动陷阱：**GPIO0 是 ESP8266 的启动模式脚，上电时按着中键会进烧录模式，不开机**。
换屏重新上电时别压到中键。

### 坑三：刷新期间完全不读键

一次三色全刷 5.1 秒，这期间 CPU 阻塞在等 BUSY 上，按键一次都采不到。
连按三下就丢三下，体感是"按了没反应"。

V15 原厂文档也提到同样的问题（按键 2 与刷新共用 IO，刷新时按会导致死机）。
目前的处理是刷新后调用 `keyResync()` 强制重新采样，并在长按上加锁（`kmLock`/`krLock`），
保证一次长按只产生一个事件、必须松手才恢复。

## 3. 按键映射：三键语义折成两键

| 操作 | 键 | 时钟页 | 菜单页 | 阅读页 | 清单页 |
|---|---|---|---|---|---|
| 短按 | 中（GPIO0） | 打开菜单 | 上移 | 上一页 | 回菜单 |
| 短按 | 右（GPIO3） | 无动作 | 下移 | 下一页 | 回菜单 |
| 长按 0.6s | 右（GPIO3） | 进菜单 | **确认** | — | — |
| 长按 0.6s | 中（GPIO0） | 整屏重刷 | **返回** | 回菜单 | 回菜单 |

**V15 原厂逻辑也实现了**：上电时按住右键（按键 3），启动直接进菜单，跳过时钟页那 11 秒。

```cpp
bool bootMenu = (digitalRead(KEY_R) == LOW);
```

菜单页 60 秒无操作自动复位回时钟页。

## 4. 刷新通道实测：只有一种模式能出画

这是本轮最重要、也最反直觉的一组数据。测试方法是**每轮先用 `0xD7`+100℃ 刷白底作画布，
再用待测模式刷棋盘格**，屏幕上真的出现格子才算成功。

| 触发字节 | 二进制 | 含 0x10（载 OTP 表） | 库内耗时 | 画面 |
|---|---|---|---|---|
| `0xC8` Mode 2 | 1100 1000 | ✗ | 90~91 ms | **全白，不出画** |
| `0xC4` Mode 1 | 1100 0100 | ✗ | 242 ms | **全白，不出画** |
| `0xCC` Mode1+2 | 1100 1100 | ✗ | 243 ms | **全白，不出画** |
| `0xF8` | 1111 1000 | ✓ | 94.3 ms | **全白，不出画** |
| `0xC0`+0x32 LUT+`0xC8` | — | — | 90.2 + 91.1 ms | **全白，不出画** |
| 裸上传+`0xC8` | — | — | 90.6 ms | **全白，不出画** |
| **`0xD7` @100℃** | 1101 0111 | ✓ | **5116 ms** | **出画** |
| **`0xD7` @65℃** | 1101 0111 | ✓ | **11225 ms** | **出画** |

结论：**这块屏（① 号 `E029A10N184274`）只认 `0xD7`（带温度覆写的三色波形）。**

### 4.1 为什么 90ms 是个陷阱

`0xC8` 那 90ms 极其稳定：不管怎么改窗口坐标、怎么改上传方式、写不写 LUT，
永远精确停在 90~91ms，抖动不超过 1ms。

这个"稳定"很容易被当成"波形确实在跑、只是画面对比度不够"。但配合画面全白来看，
更合理的解释是：**控制器里跑着一套固定相数的短波形，但没有任何墨水被驱动。**

三色屏的 OTP 通常只烧 Mode 1 那套三色波形——红色粒子需要额外的相位，
Mode 2 很可能是空的。`0xD7` 能出画，是因为它带温度覆写、走的是完整三色波形。

### 4.2 排查过程中走过的四条死路

记录下来，避免以后再走一遍。

**死路一：以为 `0x32` 写自定义 LUT 是关键。**

`epd_vm` 文件头写着「触发前要先 `0xF8` 上电并装载 OTP 波形表，再用 `0x32` 覆盖 153 字节，
否则时序照跑、BUSY 照释放、墨一点不动」。于是老老实实把 153 字节的 `LUT_BW` 表
（结构同 `GxEPD2_213_BN::lut_partial`）搬过来，按 `0xF8 → 0x32 → 0xC8` 三步触发。

还是全白。

后来翻 `bwfast.md` 才发现文档里早就写了结论：

> | P2 | 完全不写 `0x32`，直接 `0xC8` | 92 ms |
> | P3 | `0x32` 全写 `0x00` | 92 ms |
> | P5 | `0x32` 写原表 | 92 ms |
>
> **无论写什么、写不写，都是 92ms。这颗三色 SSD1680 根本不响应 `0x32`。**

**死路二：以为上电命令必须是 `0xF8`。**

`bwfast3` 里那个唯一跑通过 92ms 的函数，上电用的是 **`0xC0`**：

```cpp
static uint32_t fast08()
{
  display.epd2.expActivate(0xC0, 800);        // 只上电，不载表、不显示
  display.epd2.expWriteLut(LUT_BW, 153);      // 自定义 LUT
  return act(0xC8, 20000);                    // Mode 2
}
```

`0xC0` = `0x80|0x40`，只有时钟和模拟电源。而 `0xF8` 还含 bit4（用 OTP 的 Mode1 表装载 LUT）
和 bit3（用 Mode2 显示），它自己会跑一次 94ms 的空转显示，还会把随后写的 LUT 寄存器冲掉。

**死路三（最要命）：把横屏逻辑尺寸当物理尺寸传给了寄存器接口。**

这个固件是横屏的，画布定义是：

```c
#define W  296      // 横屏逻辑宽度
#define H  128      // 横屏逻辑高度
```

而屏的物理尺寸是 **128 宽 × 296 高**。调用：

```cpp
display.epd2.expSetRamArea(0, 0, W, H);   // ← 错
```

实际展开成 `0x44` 写 `(0+296-1)/8 = 36` 和 `0x45` 写 127，也就是
**X 地址 36（物理上限 15，直接越界），Y 只覆盖 0~127 行（物理有 296 行）**。
数据被写到一片不存在的地址区域，屏幕当然一动不动。

`0xD7` 一直好用，是因为它走 GxEPD2 内部的 `_setPartialRamArea`，那里传的是物理坐标。

修法：

```c
#define PW 128
#define PH 296
display.epd2.expSetRamArea(0, 0, PW, PH);   // 物理坐标
```

**死路四：以为 GxEPD2 的 writeImage 把数据写坏了。**

库源码里有这么一段注释：

> `writeImage` 内部调用 `_Init_Part()`，而 `_Init_Part() == _InitDisplay()`，
> 里面有 `0x12` SWRESET —— 每次上传都软复位，把 `0x32` 写进去的自定义 LUT 冲掉

于是彻底绕开库：自己维护 4736 字节物理帧缓冲，`expWriteRam(0x24)` 直接写。

```cpp
static uint8_t rawBW[4736] __attribute__((aligned(4)));

static void paintCheckerRaw()
{
  memset(rawBW, 0xFF, sizeof(rawBW));              // 1 = 白
  for (uint16_t y = 0; y < PH; y++)
    for (uint16_t x = 0; x < PW; x++) {
      if (((x / 24) + (y / 24)) & 1) continue;
      rawBW[y * (PW / 8) + (x >> 3)] &= (uint8_t)~(0x80 >> (x & 7));   // 0 = 黑
    }
  display.epd2.expSetRamArea(0, 0, PW, PH);
  display.epd2.expWriteRam(0x24, rawBW, sizeof(rawBW));
  display.epd2.expWriteRam(0x26, fastZeros, sizeof(fastZeros));
  display.epd2.expActivate(0xC8, 20000);
}
```

还是全白。

四条死路走完，结论才成立：**不是代码问题，是这块屏的 OTP 里没有 Mode 2 波形。**

### 4.3 一个还没排除的变量

`bwfast.md` 里那次「画面判据全部通过：全白干净、全黑够黑、棋盘黑白分明」的记录，
**没有写明是哪块屏**。如果当时用的是 ⑤ 号屏，那 ① 号屏 OTP 不同就完全说得通。

**下一步最省事的判定：换回 ⑤ 号屏，跑同一个固件。**
`epd_ui_fast.ino` 顶部把 `BOOT_SELFTEST` 改成 1，上电就会跑白/格交替循环。

- ⑤ 出格子、① 不出 → 屏个体差异，快刷只对部分屏有效
- 两块都不出 → 92ms 这条路从文档里划掉，`0xD7` 就是这块硬件的下限

## 5. 三色屏的两个 RAM 平面极性

踩过一次就不要再踩。`0x24`（黑白平面）和 `0x26`（红平面）极性**相反**：

| 平面 | 0 | 1 |
|---|---|---|
| `0x24` | **黑** | **白** |
| `0x26` | 非红 | **红** |

所以刷纯黑白时，`0x26` 必须整个平面写 `0x00`（全非红）。写 `0xFF` 就是整屏红。

GxEPD2 内部 `writeImage` 对 `0x26` 写的是 `~color`，菜单页 color buffer 全 0，
取反成 `0xFF`——正好是"整屏红"的输入。走 `0xD7` 时这会让底色发红，
所以 `fastFire()` 里在触发前强制把 `0x26` 重写成全 0：

```cpp
display.epd2.expWriteRam(0x26, fastZeros, sizeof(fastZeros));
```

## 6. 时钟页的半屏方案

屏幕横向 296 像素，切成两半：

| 区域 | 范围 | 内容 | 刷新方式 |
|---|---|---|---|
| 左 | x = 0~151（152px） | 日期、周几、温湿度（**红色**） | `0xD7` 三色波形，进页面时 + 每 5 分钟 |
| 右 | x = 152~295（144px） | 时间、电量、名言（黑白） | 每分钟变化时走 `GDR=144` |

```c
#define DYN_W   144
#define DYN_X   (W - DYN_W)     // = 152
```

右半动态区把 `0x01` 的门线数砍到 144，按实测公式：

```
t ≈ 0.76 s + 0.0147 s × 144 ≈ 2.88 s
```

比整屏 5.1 秒快 44%。理论上左半的红字完全不动（因为在扫描范围之外），
红色粒子不受波形影响、白拿一份保持。

**这个假设还没做视觉验证**：红色会不会因为长期不被驱动而发淡，需要实际盯 1~2 小时。

## 7. 实测耗时汇总

| 动作 | 耗时 | 说明 |
|---|---|---|
| 启动首屏（时钟页） | 11455 ms | `0xD7` @65℃，含红色 |
| 时钟 → 菜单 | 5299~5425 ms | 三色波形，一次同时清红 + 出菜单 |
| 菜单项上下移动 | 325 ms | `0xC8`，**但画面不更新（见第 4 节）** |
| 菜单 → 阅读/清单 | 354 ms | 同上，不可用 |
| 阅读翻页 | 354 ms | 同上，不可用 |

**注意**：325ms 这组数字虽然漂亮，但画面是空的。目前可用的只有 `0xD7` 那条 5.1 秒的路径。
表格保留原值是为了记录"如果快刷能出画，这里会是什么水平"。

## 8. 当前状态与待办

**可用**：

- 横屏中文时钟界面（日期/周几/温湿度/时间/电量/名言位）
- 菜单 5 项、阅读 12 页、屏幕清单三个页面
- 两键驱动 + V15 语义（右键长按确认、中键长按返回、上电按住右键直进菜单）
- 半屏彩色布局 + 右半 `GDR=144` 动态刷新

**未完成**：

1. **换 ⑤ 号屏复验 `0xC8`** —— 决定 92ms 这条路留还是删
2. **时钟页红字长期稳定性** —— 盯 1~2 小时看红色是否发淡
3. **菜单切换的 5.1 秒优化** —— 如果快刷确认无效，退路是把菜单项重排到上半屏
   （`GDR=148`），切换时间可压到约 2.94 秒
4. **蜂鸣器** —— 只有 GPIO1(TX) 或 GPIO5(SD CS) 两个夹缝，需先决定是否牺牲串口/读卡
