# 三色屏纯黑白快刷（SSD1680 / 2.9" C90c）

三色屏的标准全刷是 **27.2 秒**，这个数字由 OTP 里烧死的多相波形决定。而同样尺寸的黑白屏（IL3820）在这个项目里已经能做到 9.18ms 一帧。所以问题很自然：**三色屏能不能只驱动黑白两个态，把它当黑白屏快刷？**

能。但路上有三个坑，每一个都会让屏幕"什么都不显示"。

---

## 坑一：`0x22` 的 bit4 会把自定义 LUT 覆盖掉

SSD1680 和 IL3820 同源，`0x22`（Display Update Control 2）的位定义一致：

| 位 | 含义 |
|---|---|
| `0x80` | 开时钟 |
| `0x40` | 开模拟电源（电荷泵） |
| `0x20` | 载入温度 |
| **`0x10`** | **用 OTP 波形覆盖 `0x32` 写进去的 LUT** |
| `0x08` | Mode 2 显示 |
| `0x04` | Mode 1 显示 |
| `0x02` | 关模拟电源 |
| `0x01` | 关时钟 |

三色驱动全程用 `0xF7`，带着 `0x10`，所以永远是 OTP 的 27 秒波形。想用自己写的 LUT，触发时必须用**不含 `0x10`** 的值。

---

## 坑二：`writeNative` 把红色平面整个丢掉

`GxEPD2_290_C90c::writeNative` 的实现是：

```cpp
void GxEPD2_290_C90c::writeNative(const uint8_t* data1, const uint8_t* data2,
                                  int16_t x, int16_t y, int16_t w, int16_t h, ...)
{
  if (data1) writeImage(data1, x, y, w, h, ...);   // data2 被丢弃
}
```

三色屏的每个像素由 `0x24`（黑白平面）和 `0x26`（彩色平面）共同决定。只更新一个平面，另一个停在未知状态，屏幕不可能正确。

---

## 坑三：`writeImage` 内部会软复位，把你刚写的 LUT 清掉

`GxEPD2_290_C90c::_Init_Part()` 的实现是：

```cpp
void GxEPD2_290_C90c::_Init_Part()
{
  _InitDisplay();     // 里面有 0x12 SWRESET
}
```

而 `writeImage` 每次上传数据前都会调用 `_Init_Part()`。所以下面这个看起来最自然的顺序必然失败：

```
写 LUT → 上传数据 → 0x22 触发      ✗ 上传那一步就把 LUT 清了
```

正确顺序是：

```
设 RAM 窗口 → 写 0x24 → 写 0x26 → 上电(不含 LOAD_LUT) → 写 LUT → 0x22 触发
```

这也是为什么本轮加了两个裸通道接口，全程不调用任何 GxEPD2 高层函数：

```cpp
void expSetRamArea(uint16_t x, uint16_t y, uint16_t w, uint16_t h); // 0x11/0x44/0x45/0x4e/0x4f
void expWriteRam(uint8_t cmd, const uint8_t* data, uint32_t len);   // 0x24 或 0x26 裸写
```

---

## 坑四：`0x26` 的 1 表示红

实测：`0x26` 全写 `0xFF`，屏幕变成**红色**；全写 `0x00` 才是"非红"。

这和 GxEPD2 内部逻辑是自洽的 —— `writeImage` 写 `0x26` 时对数据取反（`_writeData(~data)`），而 `color` buffer 里 1 表示红。取反后存进 RAM 的是 0，所以 **RAM 的 0 = 红，1 = 非红**。

要刷纯黑白，`0x26` 必须全 `0x00`。喂 `0xFF` 的表现是：图案确实上去了，但背景被推成红色，而且三色波形推红需要多次翻转，看起来是红白斑驳、不均匀。

---

## 0x22 模式矩阵（实测，同一张 153 字节 LUT）

| `0x22` 值 | 含义 | 实测耗时 |
|---|---|---|
| `0xF7` | OTP 三色波形（对照） | 27,245 ms |
| `0xCC` | Mode 1 + Mode 2 | 2,955 ms |
| `0xC4` | 仅 Mode 1 | 2,954 ms |
| **`0xC8`** | **仅 Mode 2** | **92 ms** |
| `0xCF` | 含关电源位 | 3,035 ms |

同一张表，只换模式位就差了 32 倍。`92 ms` 正好等于 12 帧 × 296 行 × 31µs，而 LUT 里 TP 段 `0x0A` + `0x02` 的低半字节是 10 + 2 = 12 帧 —— **说明 Mode 2 走的才是 `0x32` 写进去的那张表**，Mode 1 走的是另一套长波形。

想用自己的 LUT，触发模式必须是 `0xC8`。

---

## 试过但走不通：缩短扫描行数

92ms 既然是 OTP 固化的，自然会想到另一条路——少扫几行，时间按比例缩。

`0x01`（Driver Output Control）的 GDR 决定扫描门线数，配合把 RAM 窗口也设成 h 行、只传 h 行数据：

| 扫描行数 | 预期（按 311µs/行） | 实测 |
|---|---|---|
| 296 | 92 ms | 91 ms |
| 148 | 46 ms | 91 ms |
| 96 | 30 ms | 90 ms |
| 64 | 20 ms | 90 ms |
| 32 | 10 ms | 91 ms |

全部 90~91ms，一毫秒没省，画面也没出来。

**`0xC8` 的 Mode 2 波形把门线数在 OTP 里写死了**，改 GDR 只影响输出范围，不影响驱动时序。之前那条"刷新耗时只跟门线数走、与面积无关"的规律属于 `0xF7`（Mode 1），Mode 2 不适用。

所以 92ms 就是这颗面板全屏黑白刷新的下限，10.8fps 是这条通路的天花板。想再快只有换面板（黑白 IL3820 在本项目里能到 109fps）。

---

## 这一路被推翻的判断

| 当时以为 | 实际 |
|---|---|
| `0x22=0xCC` 会加载自定义 LUT | `0xCC` 里 Mode 1 会盖过 Mode 2，实际走长波形 |
| `0x26` 的 1 表示"非红" | 1 表示红，要黑白必须写 0 |
| "112ms 说明 LUT 生效了" | 112ms 是空转，LUT 被 `writeImage` 内的 SWRESET 清空了 |
| 三色屏慢是因为 OTP 波形相数多 | 27 秒里有 22 秒在推红，红平面置非红后 OTP 只要 5 秒 |
| `0xC8` 快是因为 `0x32` 写的自定义 LUT 生效 | 这颗芯片根本不响应 `0x32`，92ms 来自 OTP 自带的 Mode 2 |
| 少扫几行能按比例省时间 | Mode 2 的门线数在 OTP 里写死，改 GDR 无效 |

## 实测结果（2.9" C90c，画面经目视确认）

| 项目 | 耗时 |
|---|---|
| OTP 全刷（内容带红） | 27,245 ms |
| OTP 全刷（红平面全非红） | **5,083 ms** |
| 自定义 LUT `0xC8`，10 帧 | **90~92 ms** |

画面判据全部通过：全白干净、全黑够黑、棋盘黑白分明、全程不出现红色。

两次测量（第三轮、第四轮）里，`0xC8` 五次连刷分别是 91 / 90 / 91 / 92 / 91 ms，抖动不超过 2ms，说明走的是固定相数的波形，不是空转。

### 一个被顺带推翻的判断

之前一直认为"三色屏全刷 27.2 秒"是面板固有的。实测下来：

**27 秒里有 22 秒是在推红。**

`0x26` 全置非红之后，同样走 OTP 波形，全刷只要 5.08 秒。也就是说三色屏刷纯黑白内容本来就不慢，"慢"是内容里带红造成的。这条对任何想用三色屏做黑白界面的人都成立，不需要改驱动。

---

## 自定义 LUT 为什么最后没用到

前四轮一直以为 `0xC8` 能快，是因为 `0x32` 写的自定义波形生效了。第五、六轮把它证伪了。

**第五轮**：把 LUT 的 TP 字节从 `0x0A` 一路改到 `0x02`（10 帧 → 2 帧），六个档位耗时全部是 92ms，一毫秒不差。

**第六轮**四组对照：

| 组 | 做法 | 耗时 |
|---|---|---|
| P2 | 完全不写 `0x32`，直接 `0xC8` | 92 ms |
| P3 | `0x32` 全写 `0x00` | 92 ms |
| P4 | `0x32` 全写 `0xFF` | 92 ms |
| P5 | `0x32` 写原表 | 92 ms（第五轮） |

无论写什么、写不写，都是 92ms。结论很干脆：**这颗三色 SSD1680 不响应 `0x32`**，92ms 来自 OTP 里预先烧好的 Mode 2 波形。

所以真正起作用的只有两件事：

1. `0x26` 全 `0x00`（红平面置非红）
2. `0x22 = 0xC8`（选 Mode 2 触发）

比"改驱动 + 维护 153 字节波形表"简单得多。前面几轮围绕 LUT 的折腾属于无效做功，但歪打正着找到了 `0xC8` 这个位——而它本来就在 OTP 里等着。

```cpp
// 全部实现就这两步
expWriteRam(0x26, zeros, 4736);   // 红平面全非红
expActivate(0xC8, 20000);         // Mode 2 触发，92ms
```

（153 字节黑白 LUT 的逐字节解析仍保留在 `docs/waveform.md`，那套知识在 IL3820 上是有效的，只是 SSD1680 三色不用它。）
