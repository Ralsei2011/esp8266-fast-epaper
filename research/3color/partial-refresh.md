# 区域刷的物理边界：窗口能放在任何位置，但"加速"只对顶部生效

三色 SSD1680 面板的一个长期疑问：**局刷只有半个屏幕生效，而且似乎只有竖着放才行。**
本文用一组 8 步矩阵把这个问题拆到底。初测屏：⑤（`E029A10N184299`），固件 `epd_3c_win`；
之后把同一组矩阵换成脚本在 **5 块屏**上各跑一遍，验证规律是否可复现（见文末「五屏复现」）。

---

## 结论先说

| 现象 | 判定 | 原因 |
|---|---|---|
| "只有半个屏幕能刷" | **软件问题** | 旧固件的窗口全部锚定在 `y=0`（`setPartialWindow(0,0,W,h)`），从未测过 y>0 |
| "只有竖着才能刷" | **与横竖无关** | x 方向窗口完全正常（左半屏单独刷白成功），不存在轴向限制 |
| "区域刷更快" | **物理限制，且只对顶部成立** | `0x01` GDR 只决定"扫多少行"，扫描永远从 gate 0 开始 |

一句话：**窗口地址是自由的，扫描范围是顶对齐的。** 两者一冲突，就会出现"设了窗口但屏不动"。

---

## 涉及的三个寄存器

| 寄存器 | 作用 | 关键性质 |
|---|---|---|
| `0x01` GDR | 门线数（Driver Output Control） | 决定扫描多少行，**起点固定为 gate 0**，没有"起始门线"寄存器 |
| `0x44` / `0x45` | RAM 窗口的 X / Y 起止地址 | 完全自由，窗口可放在任意 (x, y) |
| `0x4e` / `0x4f` | 写 RAM 的起始计数器 | 必须与窗口起点一致 |

三者互相独立。刷新时控制器扫描 gate `0..GDR-1`，逐个门线读取 RAM 上对应行的数据。
**如果窗口的 y 起点 ≥ GDR，那些门线根本不在扫描范围内 → 写了 RAM 也不会被驱动。**

---

## 测试矩阵

每一步：设 GDR → 设窗口 → 写 `0x24`/`0x26` → `0xF8` 上电装表 → `0x32` 覆盖 LUT → `0x22=0xF7` 触发。
关键步骤前都整屏刷黑，保证每步观察互不干扰。

| 步骤 | 配置 | 耗时 | 屏上实际表现 |
|---|---|---|---|
| S1 | 整屏黑（GDR 296） | 5119 ms | 全黑 |
| **S2** | **窗口 y=148 h=148（GDR 296）** | **5119 ms** | **下半变白、上半保持黑** ✅ |
| S3 | 整屏黑 | 5119 ms | 全黑 |
| **S4** | **窗口 x=0 w=64 h=296（GDR 296）** | **5119 ms** | **左侧竖带变白、右侧保持黑** ✅ |
| S5 | 整屏黑 | 5119 ms | 全黑 |
| **S6** | **GDR 148 + 窗口 y=148** | **2941 ms** | **完全无变化** ✅ 符合预期 |
| **S7** | **GDR 148 + 窗口 y=0** | **2941 ms** | **上半变白** ✅ |
| S8 | 整屏白 | 5119 ms | 全白 |

数据：`results/win_panel5.csv`（脚本 `tools/win_matrix.py` 采集，含每步起止秒数）。

## 耗时模型

把 296 行和 148 行两组数据代入，得到精确线性关系：

```
t ≈ 767 ms + 14.7 ms × 扫描行数
```

| 行数 | 公式 | 实测 |
|---|---|---|
| 296 | 767 + 4351 = 5118 ms | 5119 ms |
| 148 | 767 + 2176 = 2943 ms | 2941 ms |

那 767 ms 是固定开销：上电、装 OTP 波形表、BUSY 轮询。

**注意这里修正了一条早先的结论。** 之前测 `0xC8`（Mode 2）时发现"改 GDR 行数无效，32 行也是 91 ms"，
那是 Mode 2 的 OTP 波形把行数写死了。在 `0xF7`（Mode 1）这条路上，**行数是实打实生效的**，
而且是本项目唯一可控的加速手段。

## 实用recipe

### 想让顶部区域快刷
```cpp
expSetGdr(h);                    // 只扫 gate 0..h-1
expSetRamArea(0, 0, W, h);       // 窗口必须与扫描范围重合
expWriteRam(0x24, bw, W/8*h);
expWriteRam(0x26, rd, W/8*h);
expActivate(0xF8, 3000); expWriteLut(LUT_BW, 153);
expActivate(0xF7, 60000);        // ≈ 767 + 14.7*h ms
```
h=64 时约 **1.7 秒**，比整屏 5.1 秒快 3 倍。适合顶部状态栏、进度条、时钟数字。

### 想刷中间或底部区域
只能让 GDR 保持 296，接受 5.1 秒，但**画面只变那一块** ——
扫描范围外的门线读到的 RAM 内容没变，波形把它们驱动回原状态，肉眼看不到变化。

代价是整屏都吃了一遍波形（多一次闪烁 + 残影积累），收益是不用重画整屏数据。

### 不要做的事
**GDR < 296 却把窗口放在 y ≥ GDR。** 这会让耗时正常、BUSY 正常释放、屏幕上什么都不动，
是本文档里最难 debug 的一类故障——看起来像"波形没生效"，实际是地址落在扫描范围外。

## 和双色屏的对比

| | IL3820（黑白） | SSD1680（三色） |
|---|---|---|
| 局刷机制 | 差分波形，只驱动变化像素 | 无差分波形，每次跑完整多相序列 |
| 区域限制 | 任意窗口，耗时随窗口缩小 | 窗口自由，但只有顶部能用 GDR 换速度 |
| 单帧耗时 | 9.18 ms（自定义 LUT） | 5119 ms（全屏）/ 767+14.7h ms（顶部截断） |

这也解释了最早那个观察："为什么双色的就能全局局刷，而三色只有半边够局刷" ——
**双色屏的局刷是波形级别的差分，三色屏的局刷只是窗口 + 顶对齐扫描的产物。**
两者名字一样，机制完全不同。

## 五屏复现：规律从"单屏观测"升级为"型号常数"

上面的结论全部来自单块屏（⑤）。单屏数据有个隐患：你无法排除"这块屏恰好如此"。
所以把 8 步矩阵写成一个**脚本文件**（`epd_vm/win_matrix.epd`，1266 字节），
用寄存器级脚本 VM（`epd_vm/epd_vm.ino`）推给板子执行 —— 换屏只需换屏，**不重编译、不重新烧录**。

### 原始数据（`0xF7` 路径，单位 ms）

| 步骤 | 配置 | 屏① | 屏② | 屏③ | 屏④ | 屏⑤ | 极差 |
|---|---|---|---|---|---|---|---|
| S1 | 整屏黑 GDR 296 | 5067 | 5083 | 5131 | 5120 | 5119 | 64 |
| S2 | 窗口 y=148 h=148 | 5068 | 5082 | 5132 | 5119 | 5120 | 64 |
| S3 | 上半窗推黑 | 5068 | 5082 | 5133 | 5121 | 5119 | 65 |
| S4 | 左竖带 x=0 w=64 | 5068 | 5083 | 5131 | 5121 | 5119 | 63 |
| S5 | **GDR 148 + 窗口 y=148** | 2911 | 2919 | 2948 | 2942 | 2941 | 37 |
| S6 | **GDR 148 + 窗口 y=0** | 2912 | 2921 | 2949 | 2942 | 2941 | 37 |
| S7 | 整屏推黑 | 5068 | 5082 | 5132 | 5121 | 5120 | 64 |
| S8 | 中心块 64×64 | 5068 | 5083 | 5133 | 5121 | 5119 | 65 |
| S9 | 收尾整屏白 | 5068 | 5082 | 5132 | 5119 | 5119 | 64 |

五块屏最大极差 **65 ms（1.3%）**，且极差全部落在不同屏之间，同一块屏内部的重跑抖动只有 1~2 ms。

### 拟合 `t = a + b × 扫描行数`

用 S1（296 行）与 S5（148 行）两点解：

| 屏 | a（固定开销） | b（ms/行） | 半程比 S5/S1 |
|---|---|---|---|
| ① | 755 ms | 14.57 | 0.575 |
| ② | 755 ms | 14.62 | 0.574 |
| ③ | 765 ms | 14.75 | 0.575 |
| ④ | 764 ms | 14.72 | 0.575 |
| ⑤ | 763 ms | 14.72 | 0.575 |

`a` 落在 **755~765 ms**（10 ms 带宽），`b` 落在 **14.57~14.75 ms/行**（0.18 ms 带宽），
半程比五块屏全部是 **0.575**。这已经不是"差不多"，而是同一套 OTP 波形 + 同一颗内部振荡器的必然结果。

可以写进代码的常数：

```
全屏 296 行  t ≈ 5.12 s
顶部 h 行    t ≈ 0.76 s + 0.0147 s × h
```

h=64 时约 **1.70 s**，h=148 时约 **2.94 s**。这个式子对这批屏不需要按屏标定。

### 一个必须记住的假数据陷阱：BUSY 接触不良会伪装成"屏变快了"

② 号屏第一次上机时读到一组漂亮得反常的数字：整屏 **2640 ms**、半程 **1569 ms**，
恰好都是正常值的一半，拟合出的 `b` 是 7.24 ms/行 —— 看起来像"这批屏里混进了一块 2 倍速的"。

重插排线后重跑，数字回到 5083 / 2919，与其他四块一致。

原因：`waitBusy()` 靠轮询 BUSY 引脚电平判断波形何时结束。**排线没插到底时 BUSY 提前跳变，
等待提前返回，而屏其实还在慢慢刷。** 于是测出来的是一个被截断的时间。

识别特征有两条，任一条命中就该怀疑接触：

1. 整屏耗时恰好是正常值的 1/2 左右（或 1/3、1/4 这类整数比）—— 波形中途被打断不会给出这种整齐的数。
2. 反解出的 `a` 掉到 500 ms 附近（正常是 760 ms 左右）。`a` 是屏内固定开销，不该随屏变化。

`tools/run_only.py` 已内置这道体检：按步骤号判断该步应落在整屏区间（>4.6 s）还是半程区间（>2.6 s），
越界就把结果写进 `results/rejected/` 并提示重插排线，不会污染汇总表。

**这类错误比测错更危险的地方在于：它给出的是一个"更好"的结果。** 如果只看数字不看画面，
很容易当成一个惊喜发现继续往下推导，然后在错误的 `b` 上做出一整套优化方案。
