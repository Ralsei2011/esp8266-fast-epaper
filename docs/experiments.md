# 实验记录：26 个脚本对应 26 个问题

每个脚本的第一行都写了它要验证什么。跑法：

```bash
python tools/epd.py flash                          # 先烧 epd_ctl（只需一次）
python tools/epd.py run scripts/t18_charge.epd     # 跑任意一个
```

脚本会逐行发给固件，等每条命令回 `DONE` 再发下一条，
输出实时打印并落盘到 `logs/run_<时间戳>.log`。

> 说明：`scripts/` 里保留了实验当时的原始脚本，个别早期脚本用到的命令
> 在后来的固件里已经改名或加了参数（例如 `anim` 从 4 个参数扩到 8 个）。
> 它们记录的是"当时怎么问的"，不一定能在最终固件上原样重跑。

## 第一阶段：建立时基（t00 ~ t05）

| 脚本 | 问题 | 结果 |
|---|---|---|
| `t00_speed` | 快速上传到底多快，会不会崩 | `up fast` 从 11.65ms 降到 1.46ms（8×）；缓冲区必须 4 字节对齐，否则 Exception 9 |
| `t01_bringup` | 上电自检：擦屏、白底、上传、流畅度 | 建立基线：`T_FRAME=9.18ms`，单帧 = sumTP × T_FRAME |
| `t02_power` | 帧间隔加到多少才不掉电 | 早期误判：以为加 gap 有用 |
| `t03_play` | 擦白 → 静态图 → 长动画，肉眼验收 | 屏幕需要先 `hibernate()` 再 `clearScreen()` 才能真刷白 |
| `t04_demo` | 分段播放，观察流畅度 | 暴露出"80 帧必掉电"的错误结论 |
| `t05_power2` | 量化帧间隔与存活帧数的关系 | 死亡位置随机，与 gap 无单调关系 |

**这一阶段的错误结论**：以为是"帧数累积"导致掉电，于是加 gap 续命。
真正原因见 `docs/power-budget.md`。

## 第二阶段：定位掉电（t06 ~ t14）

| 脚本 | 问题 | 结果 |
|---|---|---|
| `t06_split` | 是 SPI 上传耗电，还是面板驱动耗电 | 360 次上传+扫描全活，两者都不是 |
| `t07_why` | 复位原因是什么 | `reason=0 (Power On)`，RTC 内存丢失 → 真掉电 |
| `t08_matrix` | 四组对照，找 anim 立即挂的差异 | `blink` 全屏翻转 100 帧免疫 → 排除电源总量 |
| `t09_draw` | 逐项排除绘图代码 | 画竖条挂、画圆活、只清屏活 |
| `t10_drawonly` | 同样绘图但 LUT 全 0（不驱动） | 200 帧全活 → 绘图代码干净，问题在真实驱动 |
| `t11_oldram` | `0x26` 旧帧没更新是不是主因 | 不是，但这个实验发现了"全刷刷不白"的根因 |
| `t12_thermal` | 是不是稳压器过热 | 小负载连跑 600 帧 7.8 秒没事 → 不是热 |
| `t13_vcc` | 逐帧读 VCC 看复位前是否塌陷 | ADC 被刷新干扰，读数无效（93mV），此路不通 |
| `t14_peak` | 单帧峰值电流 vs 平均功率 | 满屏翻转 300 帧 11 秒没事，6 行横条 1 帧就挂 → 与图案相关 |

## 第三阶段：找到电流阈值（t15 ~ t19）

| 脚本 | 问题 | 结果 |
|---|---|---|
| `t15_dose` | 图案宽度 / 行数 / 方向，哪个是变量 | 全宽6行挂、半宽6行活、全宽1行50帧挂、竖条活 |
| `t16_repeat` | 可复现吗 | `draw=1` 三次全挂，`draw=4` 两次全活，完全可复现 |
| `t17_edge` | 横条右边界从哪一列开始陡增 | 63 活、95 挂，阈值在 64~96 source 之间 |
| `t18_charge` | 固定最坏图案，只改驱动电荷 | **sumTP=1 全活（94.3fps），≥2 全挂** |
| `t19_long` | sumTP=1 能不能长时间跑 | **3600 帧 / 38 秒 / 零掉电 / 94.4fps** |
| `t20_demo_stable` | 稳定配置下肉眼验收 | 确认画面能动，但墨色偏淡 |

## 第四阶段：修残影与墨色（t21 ~ t25）

| 脚本 | 问题 | 结果 |
|---|---|---|
| `t21_phase` | 波形相位数与双向性的关系 | 相位数不影响双向性；要看出"哪一相是单向"得解码 VS 字节 |
| `t22_dual` | 不同 VS 字节的双向能力 | `0x10` 单向、`0x18` 双向，耗时严格 = sumTP × 9.18ms |
| `t23_scan` | 横扫整屏，看旧位置能否擦回白 | **只剩一条黑带、其余干净 → 双向成立** |
| `t24_ink` | 加长驱动能不能变黑 | TP=1/2/3 都不掉电，墨色随 TP 加深 |
| `t25_deep` | 继续加深到 TP 6 | TP=6 跑到 17.7fps 仍不掉电，用户选定此深度 |

## 第五阶段：播放链路（epd_play）

| 实验 | 结果 |
|---|---|
| 15fps 全片（3287 帧） | 跑到 2850 帧 / 208 秒后掉电，前 208 秒零中断 |
| 定位：全刷是诱因 | 关掉全刷，30fps 跑满 60.4 秒 / 1800 帧零掉电 |
| 修复全刷（切分连续驱动） | 1800 帧 / 73 秒含 2 次全刷，零掉电 |
| 60fps 尝试 | TP=1 时单帧下限约 20ms → 50fps 封顶；且 50fps 下 4~9 秒必掉电 |

## 几条可以带走的经验

1. **先确认参数真的生效了，再怀疑硬件。** 早期"LUT 改了没反应"是因为 `0x22=0x10`
   用 OTP 覆盖了寄存器，不是 IC 不接受写入。

2. **单次实验只动一个变量，并且留对照组。** `t10`（LUT 全 0，不驱动面板）是整个项目
   最有价值的一次对照 —— 它一刀把"绘图代码"和"驱动电流"分开了。

3. **做剂量-反应，而不是找"灵不灵"。** 扫右边界 63/95/111 比"换几个图案试试"有效得多。

4. **偶发问题要能被记录下来。** EEPROM 黑盒 + RTC 存活判断，让"第几帧死"变成可测数据。

5. **看到反直觉现象先别跳过。** "满屏翻转反而没事、一条横线却挂"这条线索
   直接指向了"source 线同时放电数"这个正确变量。
