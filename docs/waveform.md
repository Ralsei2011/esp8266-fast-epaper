# IL3820 波形与寄存器笔记

> 这些结论全部来自实测计时（`micros()` 包裹 BUSY 等待），不是手册抄录。
> 手册对 LUT 的字节数描述与实际行为有出入，以实测为准。

## 1. 用到的命令

| 命令 | 名称 | 本项目里的作用 |
|---|---|---|
| `0x01` | Driver Output Control | 设置有效门线数 MUX（直接决定帧时间） |
| `0x0F` | Gate Scan Start Position | 起始扫描行 |
| `0x1A` | Write to Temperature Register | 写温度值（12bit，单位 1/16 °C） |
| `0x1D` | Load Temperature | 用外部传感器温度载入 |
| `0x20` | Master Activation | 触发执行，之后等 BUSY |
| `0x22` | Display Update Control 2 | 选择本次刷新的行为（见下） |
| `0x24` | Write RAM（新帧） | 写当前帧 |
| `0x26` | Write RAM（旧帧） | 写比较基准，全刷时 IC 要用 |
| `0x32` | Write LUT Register | 写自定义波形 |
| `0x37` | Write OTP Selection | bit4=1 时改用 OTP 波形、忽略 `0x32` |
| `0x3A` | Set Dummy Line Period | 额外空扫行数 |
| `0x3B` | Set Gate Line Width | 每条门线的驱动脉宽 TGate |

## 2. `0x22` 的位定义（关键）

| 位 | 含义 |
|---|---|
| `0x80` | CLKEN，开时钟 |
| `0x40` | CPEN，开电荷泵 |
| `0x20` | 载入温度值 |
| **`0x10`** | **Load LUT：从 OTP 里按温度挑一组波形，覆盖 LUT 寄存器** |
| `0x08` | INITIAL DISPLAY（GC 全刷） |
| `0x04` | PATTERN DISPLAY（局刷，用当前 LUT 寄存器） |
| `0x02` | 关电荷泵 |
| `0x01` | 关时钟 |

**`0x10` 是这条路上最大的坑。** 直觉会以为它是"把寄存器里的波形装载进去"，实际是反的：
它把 OTP 里的波形**写回** LUT 寄存器，把你刚用 `0x32` 写的波形冲掉。

而且 OTP 选哪一组波形由温度寄存器决定，`0x1A` 的上电默认值是 `0x7FF`（=127.9 °C），
落在所有温度区间之外 → 选中一组空波形（TP 全 0）→ 刷新只用 1ms、什么也不画。

这就解释了一个曾经让人困惑的现象：只要调过一次 `0x14`（=0x10|0x04），
之后所有刷新都固定变成约 1ms 且与 LUT 内容无关。

**结论：快刷路径上绝对不要发 `0x10`。只用 `0x04`。**

## 3. LUT 寄存器结构（30 字节）

```
偏移 0..6     7 个 VS 字节，每个描述一相的 4 种像素转变电平
偏移 7..19    未使用
偏移 20..29   10 个 TP 字节，每个装 2 个时间片（低 4 位 / 高 4 位），共 20 相
偏移 144*     不存在 —— 30 字节的表只用到前 30 个
```

（`*` 某些实现会写 153 字节，但在这块屏上 30 字节与 90 字节效果完全一致，说明 IC 只读前段。）

### VS 字节怎么解

每个 VS 字节 = 4 个 2 bit 字段，对应 4 种像素转变：

| 字段值 | 电平 |
|---|---|
| `00` | GND（不驱动） |
| `01` | +VSH |
| `10` | −VSL |
| `11` | 保留 |

出厂 partial 波形的前三相解出来是：

| 字节 | 字段 | 一相的行为 |
|---|---|---|
| `0x10` | `[0,0,1,0]` | **单向**：只推一个方向，反方向是 GND |
| `0x18` | `[0,2,1,0]` | **双向**：一个 −VSL，一个 +VSH |
| `0x08` | `[0,2,0,0]` | 反向单向 |

只用 `0x10` 的快刷会"只能变黑、不能变白"，于是：

- 静止不动的块被反复同向推 → **很黑**
- 每帧只被推一次的移动物体 → **很淡**
- 移走后原地翻不回白 → **残影累积，最后整片反相**

换成 `0x18` 单相，双向立刻成立。

### 本项目用的最快波形

```
lut[0]  = 0x18      // 双向
lut[20] = TP        // 第 0 相的时间片数（1..15）
其余全部 0
```

整个表只有 2 个非零字节。TP 就是"这一帧让墨水被推几个时间片"，
是墨色和帧率的唯一旋钮。

## 4. 帧时间模型

```
T_GATE  = 31 µs                      （0x3B = 0x00）
T_FRAME = (MUX + DummyLine) × T_GATE
单帧     = sumTP × T_FRAME
```

### 验证：MUX 线性

固定 sumTP=1、DummyLine=0：

| MUX | 实测单帧 | 计算值 `MUX×31µs` |
|---|---|---|
| 296 | 9179 µs | 9176 |
| 148 | 4588 µs | 4588 |
| 64 | 1984 µs | 1984 |
| 32 | 994 µs | 992 |
| 16 | 497 µs | 496 |

误差在 3µs 以内，模型成立。

### 验证：sumTP 线性

| sumTP | 实测单帧 | 计算值 `sumTP×9176µs` |
|---|---|---|
| 1 | 9.18 ms | 9.18 |
| 2 | 18.4 ms | 18.35 |
| 4 | 36.7 ms | 36.7 |
| 7 | 64.3 ms | 64.2 |
| 14 | 128.5 ms | 128.5 |

### 为什么出厂这么慢

出厂只给两档：full 1652ms、partial 412ms。

- full = sumTP 76 × 296 行 × 约 73µs
- partial = sumTP 20 × 296 行 × 约 70µs

它的瓶颈不在 MUX，在**时间片太多**。快刷的两个杠杆就是 `sumTP`（20 → 1）和
`T_GATE`（62µs → 31µs），合起来约 45 倍。

## 5. 一个曾经走错的方向

早期做过一次"MUX 从 296 砍到 16 但帧时间不变（仍 413ms）"的实验，
当时的结论是"耗时与扫描行数无关，波形是整段播放的固定时长"。

**这个结论是错的**，原因是那次实验里没有真正把自定义 LUT 写进 IC
（LUT 被 `0x10` 用 OTP 覆盖了），跑的始终是出厂波形。出厂波形的时间片本来就打满了，
MUX 变小只是让每行少扫些像素，总时长仍由 OTPS 的整段 TP 决定。

改成"写自定义 LUT 且不碰 `0x10`"之后，MUX 立刻变成严格线性的杠杆。
**这个弯路值得记下来：当所有参数都不响应时，先怀疑参数有没有真正生效，而不是怀疑硬件。**
