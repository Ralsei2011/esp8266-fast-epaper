# 掉电定位：真正的天花板是电流，不是芯片

## 症状

播放动画时，屏上画面突然卡住，电脑端串口断开又重连，程序从头开始跑。
平均每隔几秒到几十秒一次，看起来很随机。

最初的猜测全是错的：

- ~~电池没电~~ —— 电池是满的，而且一直插着电脑
- ~~固件有 bug~~ —— 同样的代码刷静态图能跑几十秒
- ~~看门狗复位~~ —— 复位原因不是 WDT
- ~~稳压器过热~~ —— 冷机第一次跑也一样会挂
- ~~帧数累积~~ —— 加长帧间隔也不能按比例延长存活时间

## 怎么确认是"真的断电"

做了三件独立的事：

**1. 读复位原因。** `ESP.getResetReason()` 返回 `Power On`，
不是 `Exception`、不是 `Software Watchdog`、不是 `External System`。

**2. 用 RTC 用户内存做存活标记。**

ESP8266 的 RTC 用户内存（`ESP.rtcUserMemoryWrite`）在软件复位、看门狗复位、
RST 引脚复位时**内容保留**，只有 VCC 跌破阈值才**丢失**。

```
RTC 内容保留  → 非掉电（软件/看门狗/外部复位）
RTC 内容丢失  → 真掉电
```

每次复位都打印这个判据，结果全部是"已丢失(真掉电)"。

**3. 用 EEPROM 记黑盒。** 每次启动把"上次跑到第几帧、跑了多久"写进 flash，
断电也不会丢，重启后能准确知道死在哪里。这让"第 N 帧必挂"的复现变得可靠。

再加上一个旁证：**端口断开和芯片复位是同时发生的**。
那不是两个问题，是电脑 USB 口过流保护掐了 VBUS，CH340 跟着掉线重枚举。

## 关键实验：把变量隔离出来

| 实验 | 条件 | 结果 |
|---|---|---|
| 只上传不扫描 | 360 次 SPI 传输，面板不驱动 | 全活 |
| 静态图反复扫描 | 240 次，画面不变 | 全活 |
| 全屏黑白翻转 | 300 帧，每帧翻 296×128 全部像素 | 全活 |
| 弹跳圆 sumTP=4 | 600 帧 / 7.8 秒 | 全活 |
| **全宽 6 行横条 sumTP=4** | 100 帧 | **第 0~1 帧就挂（3/3 复现）** |
| 半宽（64 source）6 行横条 | 100 帧 | 全活（2/2 复现） |
| 全宽 1 行横条 | 100 帧 | 第 50~55 帧挂 |
| 竖直条（6 宽 × 全高） | 100 帧 | 全活 |

前两行说明 SPI 不是元凶，第三行说明**像素总数也不是元凶**（它比横条多得多）。
唯一相关的是"**同一时刻有多少条 source 线在放电**"。

扫右边界（保持 6 行高）：

| 右边界 source | 结果 |
|---|---|
| 63 | 200 帧全活 |
| 95 | 挂 |
| 111 / 119 / 123 / 127 | 挂 |

阈值在 64~96 条之间。超过就挂，跟画面内容复杂度无关。

## 决定性实验：固定最坏图案，只改驱动时长

画面固定成"全宽 6 行横条"（最费电的图案），只改 `sumTP`：

| sumTP | 每帧驱动时长 | 结果 |
|---|---|---|
| **1** | **9.18 ms** | **3600 帧 / 38 秒全活，94.4 fps** |
| 2 | 18.4 ms | 挂 |
| 3 | 27.5 ms | 挂 |
| 4 | 36.7 ms | 挂 |

规律非常干净：**单帧连续驱动时长 ≤ 约 10ms 时什么图案都能活，≥ 18ms 时只有小图案能活。**

注意 `sumTP` 也是帧率旋钮 —— 最省电的那一档恰好就是最快的那一档，
所以"稳"和"快"在这个项目里不冲突，冲突的是"稳/快"和"墨色"。

## 为什么加 gap 没用

试过在帧之间插 0~100ms 的延时，结果是：

| gap | 死亡位置 |
|---|---|
| 0 ms | 第 10~15 帧 |
| 40 ms | 第 35~40 帧 |
| 100 ms | 第 1 帧（偶然） |

如果是热积累或平均功率，加 gap 应该有明确收益。实际收益很弱、且随机 ——
说明触发条件是**单帧峰值电流**，不是能量累积（电容充放电的时间常数远小于帧间隔）。

## 另一条独立规律：持续驱动 > 300ms 必挂

清残影要全刷，最初写成"连做两次 174ms 的 partial 刷新"，共 **348ms 不间断驱动**。
表现是：每 600 帧触发一次全刷，几十帧之内必掉电。

修复办法是把这段连续驱动切开：

```c
expActivateTimed(0x04, 4000, &t);   // 刷一次 174ms
expPowerOff();                      // 关电荷泵
delay(250);                         // 歇一下
setFastLut();                       // 重新开泵 + 重装波形
expActivateTimed(0x04, 4000, &t);   // 再刷一次
```

修复后跑了 1800 帧 / 73 秒，含 2 次全刷，零掉电。

**结论：USB 口（或板载稳压器）的限制是"单次持续大电流的时间"，超过约 300ms 就保护。**
这跟占空比无关 —— 全屏翻转 300 帧没事（每帧只有 10ms 脉冲），
但连续 348ms 一定挂。

## 想再快/再黑，只能从硬件补

软件层面已经到边界了。要突破有两个方向：

1. **补电流**：在 5V 与 GND 之间并 470~1000µF 电解电容，靠容性储能扛过脉冲；
   或者换成能提供更大电流的独立 5V 电源（不要用电脑 USB 口）。
2. **降单帧电荷**：差分帧传输（只驱动变化的行/区域）、降低 MUX、按画面自适应 `sumTP`。

## 排查方法论

这套流程可以复用到任何"跑一会儿就重启"的嵌入式问题：

1. 先分清**复位类型**：`getResetReason()` + RTC 用户内存存活判断
2. 用 **EEPROM 黑盒**记录死前状态，让偶发问题可复现
3. **隔离变量**：SPI / 面板驱动 / 绘图代码 三条路径分开测
4. 做**剂量-反应**：固定一个维度扫另一个维度，找阈值而不是找"灵不灵"
5. 重复 2~3 次确认可复现，避免把偶发当规律
